能上网搜索的模型已经不少，真正难的是「搜得久还搜得全」。比如要整理一长串公司的 CEO 、融资轮次、官网链接，答案必须能指回网页原文。对话越长，模型越难分清：哪些字段已经核实，哪些还空着，哪条搜索思路已经证明走不通。

单智能体常见表现是反复发相似查询，预算烧完，表还缺一块。多智能体也未必更好：并行工人可能重复干活、对字段理解不一致，或者整批等待最慢的那一个。有人空着，却在等最慢的任务。

SearchOS 把计划、进度、证据和失败从对话里抽出来，做成系统里人人能读的显式状态：谁填了哪格、哪条路已死，不再靠模型在长上下文里硬记。

SearchOS 工作区：编排轨迹、并行 Agent 活动，以及关系表完成情况。先看左侧编排与右侧覆盖，能直觉到「进度在系统里，不在聊天记录里」。

先把目标写成「带引用的表」

论文把这类调研形式化成关系模式补全：先定好几张互相关联的表（像多张 Excel ），再把字段填完整，并且每一格都要标明网页出处。用人话讲，系统先回答三个问题：有几张表、每张有哪些列、表之间怎么对应，然后才开始搜。

四块共享状态： SOCM

围绕这张不断长大的表， SearchOS 做了一套搜索专用的共享工作台，叫 SOCM （ Search-Oriented Context Management ）。可以理解成所有 Agent 共用一张「进度总表」：谁填了哪格、哪条路已死，大家查同一份，不用各自翻聊天记录。时刻 

 的状态写作

四块分别是：

待填任务队列（ Frontier Task ）：把还没填完的格子变成可调度任务。每个任务带类型、状态、优先级、依赖、目标格子、指派 Agent 和尝试次数。只有依赖完成的任务才进入「现在可以开干」的集合；同一格不允许两个 Agent 同时抢；派发前还会再校验，格子若已被填满就直接关闭。

证据库（ Evidence Graph ）：存最小粒度的单条事实（一个字段值 + 来源片段），整页摘要不够用。每个节点记录取值、来源、支撑片段、绑定到哪张表的哪个实体哪个属性、置信度、来源可信度等级和状态。节点之间可以互相支持、互相矛盾，或补充细化。被拒绝或被替代的节点仍保留审计，但不计入完成度。

完成度看板（ Coverage Map ）：把每个格子标成空着 / 填好 / 不确定 / 搜不到，并记录支撑集合与冲突标记。多条证据抢同一格时，系统按固定优先级依次比：先看来源是否更权威，再看和表格字段是否对得上，最后比置信度。赢的那条写入；拿不准就标冲突，不允许悄悄盖掉旧答案。

覆盖率定义为

分母还会惩罚「表已经建好了却一行实体都没找到」的情况，防止系统只填表头、不找行，就报告高覆盖率。对「行数不固定」的表（例如所有获奖运动员会越找越多），覆盖衡量的是已知行上的完成度，并不承诺穷尽全世界。

失败记录本（ Failure Memory ）：记下无信息查询、重复查询、打不开的来源、技能失败、被砍掉的分支、被拒的主张。匹配到同类失败会累加次数，并把「不要再试」的提醒发给相关角色。没有这块，一个 Agent 刚撞过的墙，另一个还会再撞一次。

每个角色只拿到自己需要看的那部分状态：

编排器看全局缺口，搜索 Agent 看分到的格子，写作角色看压缩摘要。这份切片每次从最新状态重生，避免模型上下文里的旧快照带偏决策。

SearchOS 架构总览：编排器围绕共享状态派发缺口，工具观察经中间层写回，写作角色可选地生成带引用报告。后文模块都挂在这张图上。

流水线并行调度

角色上是一个调度员加多个工人：编排器建表结构、排优先级、决定何时停；探索 Agent 找候选实体与来源；搜索 Agent 为划定缺口收集带出处的证据；写作 Agent 产出引用报告。大家只读写同一份共享进度，不私下互聊扯皮。

调度上，它借鉴训练里「流水线并行」提高利用率的思路，换成一句工程话：前一个任务还没全部结束，空出来的工人立刻接下一个活，不必等整批齐步走完。时刻

中间件：把护栏移出 Prompt

长程搜索里，模型会丢任务状态、忽略约束；系统侧会遇到工具报错、畸形输出、死循环和预算耗尽。只靠 Prompt 提醒，很难罩住各种商用或开源 Agent 。 SearchOS 因此在模型和工具之间加了一层搜索工具中间层（ Search Tool Middleware Harness ）：

公式看起来唬人，对应的动作其实很朴素：推理前先塞对状态；工具跑完后强制落证据；再检查有没有卡住。

上下文中间件：在推理前拼近期历史、共享状态切片和检索到的技能；预算紧时优先裁旧交互，保留状态与活跃约束。

证据抽取中间件：从页面内容里抽出「实体/属性/值/来源/原文片段」候选。必须同时对得上要填的字段，且网页里能定位到对应原文，才写入证据库和完成度看板。证据成为工具执行的后果，不再依赖模型事后补记。

传感器中间件：盯着「新填了多少格」和「新增加了多少条证据」。若连续 

 步里两者都没涨，系统就认定卡住了，类似人连搜好几轮却没有任何新线索。同时它会看三项预算（迭代次数、搜索次数、真实经过的秒数）哪条最先告急，再决定继续、注入纠正、请求回填、只整理已有结果，或停掉某条分支。

分层技能：怎么搜，和怎么进某个站

SearchOS-V1 预置约 280 个技能，分三层：

•

总控流程剧本：任务拆解、表与行对齐、综合校验

•

通用搜索技巧：查询改写、实体枚举与消歧、结构化抽取、多跳与时间推理、聚合、停滞恢复，与具体网站无关

•

特定网站取数法：数据库、政府门户、百科、公司站、媒体目录；部分技能带写好的专用抓取程序，减少反复点网页、写解析

启动时注入总控剧本；每个任务再检索通用技巧与网站技能。系统会先缩小「该用哪些网站技能」的范围，再选一个执行。

关掉整套技能后， Item F1 （单个字段填对的得分）从 80.3 降到 78.3 ， Row F1 （整行所有字段都对才算分）从 56.5 降到 53.1 。同一批 100 道 WideSearch 题上，带技能时会话时间少 36.6%，搜索调用少 39.1%，页面调用少 42.7%。质量上来，试错反而更少。技能主要帮系统少走冤枉路：同样题量下，浏览次数反而明显下降。

Figure 6 ：有无技能在相同 100 道 WideSearch 题上的效率对比（误差棒为 95% 置信区间）。时间与调用量同步下降，说明收益主要来自少走弯路。

主结果：增益集中在「找全」

评测用两个基准。 WideSearch 面向大规模宽表信息收集， 200 道人工题（中英各 100 ），跨 15+ 领域，答案要落成可核验的完整表。 GISA 有 373 道贴近真实检索场景的题，答案格式覆盖单项、集合、列表、表格，便于确定性打分。

阅读成绩时先记住三个口径： Item F1 看单个字段对不对； Row F1 更严，一整行都要对才算； Set F1 看集合有没有找全。骨干上， Agent 角色用 GLM-5 ，证据抽取用 Qwen3.5-35B-A3B ；每题跑三次取最好成绩（ Max@3 ）。默认上限约 50 次编排迭代、 8 个并行子 Agent 、每子 Agent 20 次搜索、 1800 秒墙钟时间。

对照里既有 ReAct 、 Plan-and-Solve 这类单智能体，也有 Table-as-Search 、 A-MapReduce 、 Web2BigTable 等多智能体系统。 SearchOS 在两条基准的主打 F1 指标上都排第一。我更看重召回侧的抬升：对调研类 Agent ，漏一条关键实体往往比多一条噪声更伤；论文数字也支持「覆盖感知调度」首先在补漏，精确率仍保持最高一档。

消融里更值得记住的三点

表结构不该提前钉死。在 40 道可拆成多表的题上，固定单表与固定多表各有胜负；即便人为给每道题提前指定最优表结构（论文里叫 Oracle ，相当于开卷知道该用单表还是多表）， Item F1 仍比 SearchOS 低 8.2 ， Row F1 低 7.7 。 SearchOS 在这 40 题里 87.5% 选了单表、 12.5% 选了多表。关键不在人工拍板表结构，而在搜索过程中随发现的实体关系动态改表。

连续派活比齐步批次更省。这里的「齐步批次」就是等一批任务全做完再发下一批；「连续回填」就是一有空位就立刻派下一个任务，和前面的流水线调度是同一件事。在相同并发上限 

 的 WideSearch 子集上，连续回填相对批次：平均端到端时间 476s vs 629s （约 -24.3%），空闲名额实际干活比例 41.7% vs 34.6%， LLM 调用更少， Item F1 反而更高（ 86.75 vs 79.66 ）。空转主要来自「等整批」的屏障，多派工人补不上这块。

表格看起来填满了，不代表该找的条目已经找全。附录轨迹里有三个互补案例。皮尔普斯奖牌题曾出现「已知格 100% 填满，但只有 16 行，而事件规模大约三十多」。编排器检查行集合后回填，最终到 35 行。 Spotify 榜单题先锁定权威榜单的行键，再并行补元数据，避免两个榜的同一首歌被拆成两个实体。期刊论文枚举题里，付费墙触发换站策略后，系统在预算耗尽时保留未解析格子，拒绝编造字段。三件事分别对应：先定可辩护的搜索空间；把「格填满」和「行找齐」拆开；失败恢复必须有界且有出处。

边界

SearchOS-V1 强调的是把搜索中间产物做成系统状态，并为执行提供中间层与技能基础设施。大规模技能如何从数据源、轨迹和用户意图里自动合成，论文明确留给后续工作。评测是 Max@3 、固定骨干与预算；换模型、换工具栈后，数字会变，但「进度不可见 → 空转与漏填」这条因果仍然成立。

对要做长程调研 Agent 的团队，值得带走的是三条工程原则：把目标写成带引用的结构；让缺口、证据、失败进共享状态；用系统层处理停滞和预算。具体 Prompt 怎么写反而不是重点。 SearchOS 给出的是一套可运行的答案；「多智能体更强」这类口号帮不上忙。

开放域长程搜索的真正卡点，往往是系统看不见进度。模型再会搜，也会在死胡同里把预算烧光。

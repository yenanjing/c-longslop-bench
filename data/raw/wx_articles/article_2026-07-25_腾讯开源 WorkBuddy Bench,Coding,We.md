今天大家评 Coding Agent ，手里往往只有两类尺子。一类是 SWE-bench ：公开 GitHub issue 上的仓库修 bug 题，任务说明甚至解法早就在网上流转，分数升高有时更像「搜到了原 issue 」，仓库级推理未必真变强；范围也偏窄，多数是单 issue 。另一类是 CursorBench ：厂商用真实用户会话做的内部评测，分布更贴近用法，但题目不公开，外人无法核对构成，也说不清是否偏向自家 agent 。

组织里的 Coding Agent 更麻烦。同事丢过来的活，往往跨好几类：改仓库、搭前端、对 Excel 、还要处理安全告警。腾讯优图实验室、科恩实验室、 Workbuddy 、云鼎安全实验室联合放出的 WorkBuddy Bench ，就是按这种真实分工来出题，并同时回答：题目是否覆盖真实工作类型、别人能不能靠网页搜到原题、第三方能否把整条评测自己跑通。

总览：左侧从真实提交、办公流程、安全案例反推口语请求；中间四轨共用同一任务目录格式；右侧在隔离沙箱里用两套 harness 评分。

四轨各评什么，为什么故意不算总分

套件初始公开版共 260 个任务： Code 80 、 Web 70 、 Office 50 、 Security 60 。四个方向共用一套任务文件夹骨架、选题标准和执行基建，但

每轨打分方式不同

，因此报告明确不给整套总分，也不鼓励把四列分数平均成一张「总榜」。所谓文件夹骨架，就是每题一个目录，里面有口语说明、 Docker 环境和工作区；选题标准则要求：什么都不改时得分不能超过 0.3 ，标准答案应得满分 1.0 。

四子集对照：规模、领域与主指标各不相同，统一的是任务包装与双 harness 执行。

四轨被放进同一套件，核心理由是任务形状一致： agent 被扔进工作区，读一段自然语言请求，产出工件，再由它看不见的校验器打分。共享的是这个形状，四轨并不共用同一把分数尺。

抗污染：关掉「搜 prompt 」这条路

报告把最要紧的作弊路径说得很具体：公开 issue / PR 标题可被网页搜索还原，模型或 agent 只要搜到原帖，就可能走捷径。 WorkBuddy Bench 的对策是出题时重写任务描述，题目公开后也不靠藏题防作弊。

做法是：每个任务锚定真实上游提交、历史 CVE ，或具体业务场景；再按团队内部各类请求的大致占比选型；最后写成短、口语、带角色的请求，故意不写 bug 原因、不给标准补丁，也不把答案塞进提示。这样一来，用网页搜「原始 issue / PR 线程」通常对不上任务说明。

数据集本身是全开源的：任务目录、环境镜像、评测用的 agent 执行环境（ harness ）、测试与参考解都公开。抗污染因此靠「出题时已关掉可搜索 prompt 」加上数据集版本迭代，不靠把题藏起来；可选在任务里埋仅评测方知道的 canary 标记字符串；若模型输出里频繁冒出这些串，说明训练数据可能吞进了发布快照。报告也直说残余风险：模型可能早就见过原始公开代码或 CVE 分析；开源后仍可能被爬进后续训练。作者只保证做了「关掉搜题捷径」这件事，并用版本更新管理暴露，同时不声称「零污染」。

每道题打成自包含文件夹，大致是 

instruction.md

、

task.toml

、环境 Docker 、工作区，以及求解结束后才接入的评测资产。选题标准要求：什么都不改时得分不能超过 0.3 ，标准答案跑出来应得满分 1.0 ，避免「原仓库已经几乎过关」或「参考补丁也救不回来」的题混进去。所谓 hidden tests ，指的是

做题时 agent 看不到的测试

；发布后测试套件与参考解一样公开，第三方可审计。

评测统一跑在隔离沙箱：无外网、无外部账号、无密钥。两套 agent harness ，也就是实际驱动 Coding Agent 的工具壳，分别是 CodeBuddy Code （下文简称 cbc ）与 Claude Code （简称 cc ）。同一模型换壳，分数和名次都可能变，所以后面榜单要分八列看，不能混成一张总榜。

Code ：口语需求 + 隐藏测试，修 bug 只占一小块

Code 子集问的是：面对一段角色扮演过的工程请求， agent 能否在完整开源仓库里定位、修改，并让隐藏测试变绿。 80 题里， bug 修复只有 10 题；其余覆盖功能与接口、代码工程、测试、算法工程、产品/数据分析等。请求方角色有五类：开发、算法、产品、质量保障、运维。

来源分三类： 34 题锚定真实上游提交（论文称 Family A ：保留仓库结构，但把原始提交语境改写成口语任务）； 24 题是不看原实现、按公开 API 自己重写一版（含 4 题跨语言移植到 Python ）； 22 题是人工搭的模拟项目，专门练角色工作流。难度主要来自跨模块「该改哪里」，算法本身往往不是瓶颈。

Code 六大用量域与 Web 七类任务、六种生命周期； Code 里 bug 修复仅 10/80 ， Web 里从零搭建占 35/70 。

Code 流程：读口语请求 → 探索仓库出补丁；主指标是隐藏测试分。 LLM 打分只作参考，不算正式成绩。

结果侧有个稳定缺口：数据与算法类任务平均大约 74%，狭义改仓库代码大约 65%。报告的读法是：前者难在业务语义，代码本身往往不难；真正拉开差距的，是在现有接口约定下精确改真实仓库。按更细类别，最难两档是修真实回归（

bug_fix

）与保住接口约定（

api_contract

），均值约 0.47 ；相对容易的是明确规格的合成流水线与写测试。产品分析类分数跨度极大（约 0.08–1.00 ），成败常取决于有没有读懂口语里的业务约束。例如需求说「别把隔太久才发生的购买算进转化」：高分模型会按时间窗口过滤，低分模型代码能跑，却把每笔购买都算进去。这更像在考「听懂同事那句含糊约束」，会写循环远远不够。

Web ：交付物要能交互，规则、视觉与 agent 裁判一起查

Web 面向前端交付物：从零搭建、修改扩展、评审转换都有。评测会盯最终结果做三类检查：写死的规则检查格式与可执行约束；多模态模型看文本、结构与视觉；另一个 agent 实际点页面，查交互流与状态。

Web ：从查询与完整跑题过程到交付物，再用规则、多模态裁判与 agent 裁判对照证据打分。

切片结果里，视觉设计与分析报告相对强；页面交互与数据可视化语义更弱。有状态、多步流程、本地持久化与跨状态行为，是最难的一块。常见丢分点是：数据存在哪、页面显示什么、刷新后还在不在、最终提交内容这四件事对不齐。页面看起来像样，点下去却在中途断掉。当前 agent 多数能搭出壳子，真正拖后腿的是状态机与持久化。

Office ：多文件交接，规则分与语义裁判按题加权

Office 50 题模拟本地多格式文件工作区： xlsx / csv / pdf / docx 混用， agent 要把信息带到可交接的交付物里，并保持跨文件一致。评测看最终可核对的工作区状态：文件、结构、状态变化、证据与执行边界。有些题先看文件字段对不对（规则），有些还要看说明是否写清（语义），所以每题自定两者权重，避免一刀切。每题先跑确定性规则（文件是否改对、字段是否一致），再用 LLM Judge 看语义是否达标；规则通常占大头（约 0.70–0.95 ），最后对所有题求平均。举例：规则占 0.8 、语义占 0.2 ，规则得 1.0 、 Judge 得 0.5 ，该题就是 0.9 。

Office ： agent 改工作区后，规则查可核对状态， Judge 只看固定证据；两分按题加权后再对所有题平均。

难度校准后，跨模型均值从 easy 到 hard 单调下降（ cbc 约 84.6 → 80.3 → 73.1 ； cc 约 83.9 → 78.9 → 72.0 ）。任务类型上，模型强弱也不一样：有的更擅长把多张表对齐核对，有的更擅长算指标、执行复杂规则或抽结构化字段。低分交付物里反复出现同一类问题：相关文件互相矛盾、记录对不上来源、结构化文件解析失败，或者没自检就交卷。哪怕单份文档看起来像样，整条交接仍会丢分。 Office 测的是「能不能把活交出去」，单文件好看不够。

Office 按难度与任务类型切开：总体随难度下降，不同类型上的榜首模型并不相同。

Security ：红蓝队六类任务，程序打分、不用 LLM 裁判

Security 60 题覆盖白盒源码审计、黑盒二进制利用、 Web 利用、 agent 安全、恶意软件分析与安全运营等；按攻防角色粗分，攻击向 38 题、防守分析向 22 题。白盒发现类锚定真实历史 CVE ，重建为可复现沙箱。每题在隔离 Docker 里跑确定性 

scoring.py

 给出 0–1 分，并叠多层防投机检查；全轨不用 LLM 裁判。

Security ：从真实漏洞与自写场景做成可复现用例，六类红蓝任务，容器内程序打分。

这轨也是换 harness 后分差最大的一块：七个双测模型平均绝对分差约 8.6 。安全口吻请求还会触发拒答。例如 Claude Opus 4.8 在 Claude Code 下累计 13 次直接拒绝做题（ CodeBuddy Code 下为 0 ）， GPT-5.5 在 CodeBuddy Code 下有 2 次。拒答按未完成计入，会拉低该列均分；榜单仍按实际跑完的三次平均计入。安全轨因此同时在测能力与策略：会不会做，以及敢不敢做。

榜单：没有一家通吃，开源权重也能拿下两列

读榜分三步。先认列名： Code@cbc 表示 Code 轨在 CodeBuddy Code 下、开启深度推理（ think ）模式、三次运行的均值；同一轨不要跨 harness 比高低，同一 harness 内再比模型。再单独看 ‡： Claude Opus 4.8 的 Code@cc 除了关闭提问工具，还额外加了「不要提问、一次做完」类指令，与其它格子不完全同条件。最后才读八列榜首；报告也强调不要跨子集比绝对分。

主榜：八列各有榜首；带 ‡ 的 Code@cc 为改指令配置，读榜时单独看待。

八个计分列的榜首拆成三家：

■

Claude Opus 4.8 拿下五列： Code 双 harness （ 74.43 / 77.90‡）、 Web 双 harness （ 68.14 / 69.86 ）、 Office@cbc （ 82.37 ）。

HY-3 在 Office@cbc 以 82.08 紧贴榜首；它也是少数在 Web 上高于 Code 的配置之一（ cbc 下 67.71 vs 62.90 ）。

harness 会改变测量结果。 Code 上名次会换： cbc 下 GPT-5.5 （ 72.90 ）高于 GLM-5.2 （ 71.54 ）， cc 下则反过来（ 76.63 vs 77.06 ）。 Web 在 cc 下有升有降， GLM-5.2 掉 6.72 分。 Office 最稳，多数模型绝对位移不到 2 分。 Security 重排最狠： GPT-5.5 从 cbc 第六爬到 cc 第二（ 64.39 → 77.91 ）， MiniMax-M3 则从第二掉到第五。

效率也不跟排名一条线。 CodeBuddy Code 下， GPT-5.5 在四轨的输出 token 预算都是全场最小（ Code 约 6.9k 、 Web 13.5k 、 Office 10.2k 、 Security 7.5k ）， Code / Office 仍处第一梯队。反过来， DeepSeek-V4-Flash 在 cc 上 Code 输出约 28.6k ，比 GPT-5.5 的 8.7k 多约 3.3 倍，分数却低 14.74 分。 Security 最吃轮次与上下文： MiniMax-M3 在 cbc 下平均约 88.8 轮、含缓存输入约千万级 token ，才换到 74.14 。接入细节也会动分：诊断复跑里给 HY-3 打开「上一轮思考内容传给下一轮」后， Code 分别 +3.82 （ cbc ）/ +1.92 （ cc ）；主榜仍报标准配置。

边界：公开可审计，同时接受开源后的暴露

报告写清几条硬边界。 Code 公开集以 Python 为主，跨语言只有少量移植题，结论不宜直接外推到其他语言生态。 Judge 类组件（ Web 的多模态/agent 裁判、 Office 的语义裁判）存在模型偏好风险； Code / Security 正式成绩刻意压在确定性校验上， Office 用固定证据与规则分压低但仍消除不了 Judge 偏差。公开全套任务后，内容可被爬进未来训练，抗污染要靠版本迭代替换「已显脏」的题，不靠藏题。 Claude Opus 4.8 的 Code@cc 一格条件略不同，读榜时要带着 ‡ 看。

若把选型缩到「只看仓库修 bug 」，前端状态机、办公交接与安全作业上的差距会被漏掉；若只信闭源生产榜，又很难审计题目是否偏向某一家 harness 。这套基准不能合成总分，读分必须分轨、分 harness ；好处是第三方能完整复现和审计题目构成，提示形态也更接近「同事口头丢活」。

按论文口径，题库公开后迟早会被刷熟，换题是常态。选型时我更在意自己业务最常踩坑的那一轨：前端状态断了、办公文件对不上、还是安全请求被拒。当期榜首会变，这些失败形态短期内不会消失。一个实际用法是：先用本套件的失败切片对自家 agent 做回归，再决定要不要追某一列榜首；否则很容易为了一个会滚动的总分，把产品能力做成「会刷题」。

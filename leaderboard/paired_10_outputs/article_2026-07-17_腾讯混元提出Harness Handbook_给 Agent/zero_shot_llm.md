腾讯混元 HY LLM Frontier 提出 Harness Handbook：把 Agent harness 的「行为」整理成一份可导航、可校验、还能跟着代码一起更新的手册。它想让负责改代码的智能体先找齐该动的地方，再去写编辑计划。

Harness Handbook: Making Evolving Agent Harnesses Readable, Navigable, and Editable

给一个编码 Agent 加条规矩——「删文件前必须问用户」——听上去是个很小的需求。

真动手就散了。系统提示里可能写着安全规则，工具包装层可能决定删除操作放不放行，状态管理里存着用户授权，配置里还有个绕过确认的开关，遥测那边又要记下这次危险操作。你去搜 delete、confirm、permission，搜出来的基本都是碎片。

漏掉哪一块都不行：提示词明明要求确认，某条执行路径照样能绕过去。尴尬就出在这儿。

论文要解决的就是这件事。现在的 Agent 外面都套着一层 harness：提示怎么拼、工具怎么调、状态怎么传、失败怎么处理、权限怎么查，全归这层软件管。模型升级、工具 API 换了、产品需求变了，harness 也得跟着改。

难就难在，改需求说的是「行为」，仓库里摆的却是「文件」。开发者——或者负责改代码的智能体——得先搞清楚「这个行为到底写在哪些代码里」。论文管这叫行为定位。

Harness Handbook 的想法其实很朴素：别让智能体对着文件树硬猜行为。先把仓库整理成一张行为地图，再让它顺着地图去找源码证据。

**行为地图先于文件清单**

Harness Handbook 第一个关心的问题是「这个系统跑起来会做哪些事」。文件清单只是入口，行为链才是主线。

论文里的手册分三层。第一层是系统总览，讲架构、执行模型、主要阶段和全局数据流。读完这层，你大概知道这个 Agent 是怎么跑起来的。

第二层是阶段和组件：初始化、规划、工具调用、观察回写、终止判断，各自负责什么，输入输出是什么，依赖哪些状态。

第三层才落到源码。它不光写「这里有个函数」，还会说明这段代码负责什么行为、读写哪些状态、异常怎么走，并给出能回到当前仓库的源码定位器。

这三层真正管用的地方，是把「我要改一个行为」翻译成「我该查哪些代码和状态」。拿权限确认来说，错处往往不在某个函数本身，而在状态从规划阶段传到工具执行阶段时，被谁给覆盖了。

开发者看到的是一条行为链，智能体拿到的是可验证的代码位点。状态索引也重要，因为 harness 里的很多 bug 不在单个函数里，而出在状态跨阶段传递的时候。

手册有条底线：源码说了算。一个 L3 条目必须能在当前仓库里重新校验；校验不过就冻结，不能拿去继续定位。这就避开了最常见的文档病——代码早变了，文档还装作自己是对的。

**手册怎么从代码里长出来**

论文没假设有人手写一本厚手册，它给的是一套自动构建流程。

这里说的「叶」，就是手册最终指向的最小单位。仓库结构清楚时，可以细到某个函数；仓库太大、阶段不明时，就先粗到某个文件，免得一开始就把上下文预算烧光。

第一步是静态分析。系统解析仓库里的函数、方法、类、外部边界、调用关系和状态访问，做出一张带源码位置的程序图。能解析就记下来；解析不了的调用不硬猜目标，只写进 unresolved log。

第二步才上模型，目的是给代码贴行为标签。这里有两种粒度。

如果仓库的执行阶段本来就清楚——比如已经有一份可信的阶段骨架——就用函数作叶。一个 L3 条目可以对应一个函数，也可以对应函数里一段连续区域。实验里的 Terminus-2 走的是这条路。

如果仓库太大、阶段得靠推断，或者按函数展开会超预算，就用文件作叶：先给文件做职责卡片，再推断阶段结构。实验里的 Codex 走的是这条路。

最该留意的是，「不完整」会被明确留下来。没覆盖到的文件、没法稳定分类的逻辑、解析不了的调用，统统记进记录。对改代码来说，老实暴露缺口，比装成一张完整地图有用得多。

第三步是合成和打包。系统把阶段结构写成 L1、L2、L3 文档，把每个 L3 重新锚回源码，再留下后续定位和同步要用的结构化数据。

**改代码时，智能体怎么用它**

有了手册，修改流程变成四步。

第一步，BGPD 先定位。BGPD 全称 Behavior-Guided Progressive Disclosure，可以理解成「按行为逐层展开」：先在系统和阶段层确认相关行为，再钻到具体单元，最后把候选位点拿到当前仓库里校验。

第二步，规划器据这些证据写编辑计划。计划不只是「改某个文件」，还得解释为什么这些位点和请求有关、哪些范围不该碰。

第四步，只要仓库产生了非空 diff，手册就得同步更新：先重校验源码定位器，再决定是只刷新受影响的条目，还是重跑一套更大的组织流程。解析不了或分不了类的内容会被冻结、记进覆盖记录，不让它们混进正文制造假确定性。

这一步决定手册会不会变成又一本过期文档。很多团队的问题不是没写文档，而是代码改了三轮，文档还停在第一版架构图上。Harness Handbook 把重同步写进工作流，说白了就是：行为地图必须和仓库同版本。

**实验真正想证明什么**

论文评测聚焦在更靠前的一步：给一个自然语言修改请求，规划器能不能找对实现位点、写出更好的编辑计划。自动合入补丁不在这次实验范围内。

这是主动把问题面缩小：先切到 Agent 改代码最容易出错的第一步。位置找错了，后面测试再多，也是在错误的方向上补救。论文先证明「找位置」能改善，边界反而更清楚。

对照很干净。Baseline 直接探索仓库；Handbook-Assisted 用手册加 BGPD 导航。两组的请求、仓库、模型、工具权限和解码设置都一样。规划器用的是 DeepSeek-V4-Pro，计划质量交给 GPT-5.5、Opus 4.8、DeepSeek-V4-Pro 三个评委独立判断。

评委看三件事：定位准不准、改动范围会不会铺太宽、推理证据够不够。定位权重最高，占一半。

实验对象是两个开源 harness：Codex 和 Terminus-2，每个 30 条行为驱动的修改请求。请求分三类——改已有行为但不给目标位置的 Query、请求跨文件能力的 Cross-file，以及关键词很难命中的 Search-Hostile。

**计划更好，token 还更少**

Codex 上，手册辅助规划的胜率从 28.3% 提到 38.3%；Terminus-2 上，从 26.7% 提到 45.6%。三个评委方向一致，说明不是某个评委模型的偏好在起作用。

token 也降了。Codex 平均规划 token 从约 10.2 万降到 8.9 万，Terminus-2 从约 5.8 万降到 5.3 万。手册减少了无关探索，模型不是靠堆长上下文硬撑出来的。

不过这提升也不能读成「有手册就稳了」。Codex 上 38.3% 的胜率仍然不高，它更像是把一部分乱搜仓库的时间省下来，让规划器少走点弯路；离确定性的代码修改流程还远得很。

拆开看分项，收益最直接落在定位上：手册先帮智能体少找错地方，范围控制和推理跟着改善，但幅度小一些。这符合直觉——找点找错了，后面计划写得再漂亮也没用。

**弱规划器更接近强模型的位点判断**

论文还做了个更细的检查：把规划器预测的编辑位点，跟 Opus 4.8、GPT-5.5 独立写出的参考计划对齐，看文件级和符号级的召回、精确率、F1，还有 Wrong。

Wrong 指的是预测与参考计划零重叠的比例，越低越好。

Table 1：相对 Opus 4.8 / GPT-5.5 参考计划的定位指标。文件级和符号级的召回、精确率、F1 共 24 组，Handbook 全部更高；Wrong 最大下降 25.9 个百分点。

这张表最要紧的是一致性：两个 harness、两个参考模型、文件级和符号级，召回、精确率、F1 全部提升，F1 增益在 5.0 到 18.8 个百分点之间。

召回和精确率一起升，说明提升来自更准的位点集合；Wrong 也降了，完全找错方向的情况变少。Codex 对照 Opus 4.8 的符号级 Wrong 从 44.4% 降到 18.5%，这是实打实的差距。

但这里也得克制。参考计划毕竟也是模型写的，不能当人工金标准。这个实验说明的是：在定位任务上，「弱规划器 + 好地图」更接近强模型的位点判断，没证明所有位点都绝对正确。

**最适合关键字不友好的改动**

按请求类型拆开，六组 harness × 类型对比都偏向 Handbook。Codex 在 Query 请求上抬得最多，Terminus-2 在 Search-Hostile 请求上抬得最多，跨文件请求也有两位数的百分点收益。

这部分给工程侧的启发更直接：改动要是集中在一个大家都知道的热文件里，手册的价值有限；可一旦行为跨阶段、跨状态、跨模块，关键词又飘忽不定，行为地图就开始值钱了。

所以它也替代不了所有代码搜索。改按钮文案、改一个已知配置项，用 grep 可能更快。真正适合它的，是那种需求说的是「行为」，代码里却没有同名函数，还牵扯提示词、状态和工具边界的改动。

这也解释了为什么 harness 特别适合这套方法。普通业务函数常常能靠调用链和测试覆盖来定位；Agent harness 的行为更像一份运行时协议，很多关键逻辑藏在提示、状态、工具边界和异常分支里。

**它离自动自我进化还有多远**

论文附录里展示了手册怎么以 SKILL.md 的形态暴露给规划器。

这张图有点像给未来工作埋了个接口。真正难的是让手册一直可信：阶段标签准不准，源码锚点会不会漂，diff 之后有没有及时重同步，覆盖缺口有没有暴露出来。

所以论文的边界也很清楚：它解决的是改前的定位和编辑计划，不保证改后行为正确。合入、测试、回归、旁路审查，还是得靠现有工程流程。

我更愿意把 Harness Handbook 看成一层「行为索引」。它夹在仓库和负责改代码的智能体之间，专门回答一个问题：这条行为，是怎么在代码里长出来的。

如果未来的 Agent 真要长期维护自己的 harness，光会写补丁不够。它还得知道补丁该落在哪里、凭什么说这些位置算完整、改完后手册有没有跟着变。缺了这层行为地图，所谓自我进化，很容易变成一次次带着高置信度的盲改。

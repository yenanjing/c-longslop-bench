腾讯混元 HY LLM Frontier 提出了 Harness Handbook，它说的是把 Agent harness 的「行为」整理成可导航、可校验、可随代码更新的手册，让负责修改代码的智能体先找齐该改的位置，再写编辑计划。

Harness Handbook: Making Evolving Agent Harnesses Readable, Navigable, and Editable给一个编码 Agent 加上「删文件前必须询问用户」，听起来像一条很小的需求。

真正动手的时候，问题其实会变得很散，也就是说系统提示里可能有安全规则，工具包装层可能决定文件删除是否放行，状态管理里可能保存用户授权，配置里可能有绕过确认的开关，遥测里还会记录这次危险操作。搜 delete、confirm、permission，通常只能搜到碎片了。

漏掉任何一块，都可能出现很尴尬的结果，说的是提示词写了要确认，某条执行路径却仍然能绕过去了。

这就是论文要处理的问题了。今天的 Agent 外面有一层 harness，也就是提示怎么拼、工具怎么调、状态怎么传、失败怎么处理、权限怎么检查，都是这层软件在管。模型升级、工具 API 变化、产品需求变化时，harness 也要跟着改了。

难点在于，修改请求说的是行为，仓库摆放的是文件。开发者或负责修改代码的智能体得先把「这个行为到底写在哪些代码里」找齐。论文把这件事叫行为定位。

Harness Handbook 的核心想法很朴素，说的是别让智能体从文件树里硬猜行为。先把仓库整理成一张行为地图，再让它沿着地图去找源码证据了。

行为地图先于文件清单。Harness Handbook 关心的第一问题是「这个系统运行时会做哪些事」。文件清单只是入口，行为链才是主线。

论文里的手册分三层，也就是说第一层是系统总览，回答架构、执行模型、主要阶段和全局数据流。读到这里，大概就知道这个 Agent 是怎么跑起来的了。

第二层是阶段和组件。比如初始化、规划、工具调用、观察回写、终止判断，各自承担什么责任，输入输出是什么，依赖哪些状态。

第三层才落到源码。它不只写「这里有个函数」，还会说明这段单元逻辑负责什么行为，读写哪些状态，异常情况怎么走，并给出能回到当前仓库的源码定位器。

这三层真正有用的地方，在于把「我要改一个行为」翻译成「我该检查哪些代码和状态」。比如权限确认这类需求，错点往往不在某个函数本身，而在状态从规划阶段传到工具执行阶段时被谁覆盖了。

开发者看到的是一条行为链，智能体拿到的是可验证的代码位点。状态索引也很重要，因为 harness 里的很多 bug 不在单个函数里，而在状态跨阶段传递时发生。

手册还有一个底线，说的是源码仍然是权威。一个 L3 条目必须能在当前仓库里重新校验，校验失败，就冻结，不能继续拿来定位。这样做避免了最常见的文档病，也就是代码早变了，文档还在装作自己正确。

手册怎么从代码里长出来。这篇论文没有假设人手工写一本厚手册。它给的是自动构建流程。

这里的「叶」可以理解成手册最终指向的最小单位。仓库结构清楚时，它可以细到某个函数；仓库太大或阶段不清楚时，就先粗到某个文件，避免一开始就把上下文预算耗光。

那么接着上面源码校验这个话题，第一步是静态分析。系统解析仓库里的函数、方法、类、外部边界、调用关系和状态访问，形成一个带源码位置的程序图。能解析就记录下来，不能解析的调用不会硬猜目标，只写进 unresolved log 。

第二步才引入模型，目标是给代码贴行为标签。论文有两种粒度。

如果仓库的执行阶段本来就清楚，比如已有可信的阶段骨架，就用函数作叶。一个 L3 条目可以对应一个函数，也可以对应函数里的连续区域。实验里的 Terminus-2 用的是这条路。

如果仓库太大、阶段要靠推断，或者函数级展开会超预算，这时候我们干脆用文件来作叶。那具体来说，系统先给文件做职责卡片，再据此推断阶段结构。实验里的 Codex 走的就是这条路。

这里最值得注意的是「不完整」会被显式留下来。没覆盖到的文件、无法稳定分类的逻辑、解析不了的调用，都进入记录。对代码修改任务来说，诚实暴露缺口，比伪装成完整地图更有用。

顺着上面这条路继续往下，第三步是合成和打包。系统把阶段结构写成 L1 、 L2 、 L3 文档，把每个 L3 重新锚回源码，并留下后续定位和同步需要的结构化数据。

改代码时，智能体怎么用它。有了手册，修改流程变成四步。

第一步， BGPD 先做定位。 BGPD 的全称是 Behavior-Guided Progressive Disclosure ，可以理解成「按行为逐层展开」。它先从系统和阶段层确认相关行为，再钻到具体单元，最后把候选代码位点拿到当前仓库里校验。

第二步，规划器基于这些证据写编辑计划。这里的计划不只是「改某文件」，还要解释为什么这些位点和请求有关，哪些范围不该碰。

第四步，只要仓库产生非空 diff ，手册就要同步更新。这里的同步，我们分两步走，先重校验源码定位器，再决定是只刷新受影响的条目，还是重新跑更大的组织流程。至于那些无法解析或无法分类的内容，会被冻结或者记进覆盖记录，免得混进正文制造假确定性。

这一步决定手册会不会变成又一本过期文档。很多团队的问题不是没写文档，而是代码改了三轮以后，文档还停在第一版架构图里。Harness Handbook 把重同步写进工作流，这本质上说的是，行为地图必须和仓库保持同一个版本，不能落后了。

那么顺着上面这个边界更清楚的思路，我们接着看实验真正想证明什么。那具体来看，论文评测聚焦在更靠前的一步，说的是给定自然语言修改请求，规划器能不能找对实现位点，写出更好的编辑计划。自动合入补丁不在这次实验范围内了。

这是一种主动缩小问题面的评测设计，也就是先切到 Agent 改代码最容易出错的第一步。位置找错了，后面测试再多，也是在错误方向上补救了。论文先证明「找位置」能改善，边界反而更清楚了。

把边界收清楚之后，我们再看对照方式，做得很干净。Baseline 直接探索仓库；Handbook-Assisted 用手册和 BGPD 导航。两组请求、仓库、模型、工具权限和解码设置一致。规划器使用 DeepSeek-V4-Pro ，计划质量由 GPT-5.5 、 Opus 4.8 、 DeepSeek-V4-Pro 三个评委独立判断。

你看，评委其实就看三件事，说的是定位准不准、改动范围会不会过宽、推理证据够不够充分。这里头定位权重最高，占了一半呢。

实验对象嘛，是两个开源 harness，也就是 Codex 和 Terminus-2。每个 harness 有 30 条行为驱动的修改请求。请求分成三类，说的是改已有行为但不给目标位置的 Query、请求跨文件能力的 Cross-file，还有关键词搜索很难命中的 Search-Hostile。

计划更好， token 还更少。Codex 上，手册辅助规划的胜率从 28.3% 到 38.3%。 Terminus-2 上，从 26.7% 到 45.6%。三个评委的方向一致，说明结果不是某个评委模型偏好导致的。

性能这块刚说完，再来看成本，token 也跟着降了。你看 Codex 平均规划 token 从约 10.2 万降到 8.9 万，Terminus-2 呢，从约 5.8 万降到 5.3 万。手册减少了无关探索，模型也没靠更长上下文硬撑结果，是吧。

但这个提升也不能读成「有手册就稳了」。 Codex 上 38.3% 的胜率仍然不高，它更像是把一部分乱搜仓库的时间省下来，让规划器少走错路；距离确定性的代码修改流程还很远。

从分项来看，收益最直接地体现在定位上。手册先帮智能体少找错地方，范围控制和推理才跟着改善，不过幅度比较小。这个结果挺符合直觉的，也就是找点找错了，后面的计划写得再漂亮也没用嘛。

弱规划器这就更接近强模型的位点判断了。论文还做了一个更细的检查，说的是把规划器预测的编辑位点，跟 Opus 4.8、GPT-5.5 独立写出的参考计划对齐，去看文件级和符号级的召回、精确率、F1，还有 Wrong。

Wrong 指的是预测与参考计划零重叠的比例，越低越好。

你看 Table 1 说的是相对 Opus 4.8 / GPT-5.5 参考计划的定位指标。文件级和符号级的召回、精确率、F1 一共 24 组，Handbook 全部更高，Wrong 呢，最大下降 25.9 个百分点。

这张表最要紧的就是一致性，说的是两个 harness、两个参考模型、文件级和符号级，召回、精确率、F1 全都提升了。F1 增益在 5.0 到 18.8 个百分点之间呢。

召回和精确率一起升，说明提升来自更准的位点集合。 Wrong 也下降，完全找错方向的情况变少。 Codex 对照 Opus 4.8 的符号级 Wrong 从 44.4% 降到 18.5%，这是很实在的差距。

但这里也得克制一点理解。参考计划仍然是模型写出来的，不能当成人工金标准。这个实验说的是，在定位任务上，「弱规划器 + 好地图」更接近强模型的位点判断，不过它没有证明所有位点都绝对正确呢。

位点判断先放到一边，这里要说的是，最适合关键字不友好的改动。按请求类型拆开看，六组 harness × 类型对比都偏向 Handbook。Codex 在 Query 请求上抬得最多，Terminus-2 呢，在 Search-Hostile 请求上抬得最多，跨文件请求也有两位数百分点收益，对吧。

这部分给工程侧的启发就更直接了，说的是如果改动集中在一个大家都知道的热文件里，手册的价值就有限，可要是行为跨阶段、跨状态、跨模块，关键词又不稳定，行为地图就开始值钱了。

所以它不适合拿来替代所有代码搜索。改按钮文案、改一个已知配置项，用 grep 可能更快；真正适合它的，是那种需求说的是「行为」，但代码里没有同名函数、还牵涉提示词、状态和工具边界的改动。

这也解释了为什么 harness 特别适合这类方法。普通业务函数常常可以靠调用链和测试覆盖定位； Agent harness 的行为更像运行时协议，很多关键逻辑藏在提示、状态、工具边界和异常分支里。

它离自动自我进化还有多远。论文附录里还展示了手册如何以SKILL.md形态暴露给规划器。

这张图有点像给未来工作埋接口。真正难的是让手册持续可信，说的是阶段标签准不准，源码锚点会不会漂，diff 后有没有及时重同步，覆盖缺口有没有暴露出来，对吧。

所以这篇论文的边界也很清楚。它解决的是改前定位和编辑计划，不保证改后行为正确。合入、测试、回归、旁路审查，仍然要靠现有工程流程。

说白了，我更愿意把 Harness Handbook 看成一种「行为索引层」。它介于仓库和负责修改代码的智能体之间，专门回答一个问题，也就是这条行为是怎么在代码里长出来的。

如果未来的 Agent 真的要长期维护自己的 harness ，只会写补丁不够。它还得知道补丁该落在哪里、为什么这些位置算完整、改完后手册有没有跟着变。缺了这层行为地图，所谓自我进化很容易变成一次次带着高置信度的盲改。

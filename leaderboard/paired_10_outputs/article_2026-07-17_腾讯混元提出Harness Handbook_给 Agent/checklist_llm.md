腾讯混元 HY LLM Frontier 提出 Harness Handbook。它把 Agent harness 的「行为」整理成手册。这本手册可导航、可校验，还能随代码更新。负责改代码的智能体先找齐该改的位置，再写编辑计划。

Harness Handbook: Making Evolving Agent Harnesses Readable, Navigable, and Editable

给一个编码 Agent 加上「删文件前必须询问用户」。听起来像一条很小的需求。

真正动手时，问题会变得很散。系统提示里可能有安全规则。工具包装层可能决定文件删除是否放行。状态管理里可能保存用户授权。配置里可能藏着绕过确认的开关。遥测里还会记录这次危险操作。搜 delete、confirm、permission，通常只搜到碎片。

漏掉任何一块，都可能出现很尴尬的结果——提示词写了要确认，某条执行路径却能绕过去。

这就是论文要处理的问题。今天的 Agent 外面有一层 harness。提示怎么拼，工具怎么调，状态怎么传，失败怎么处理，权限怎么检查，都由这层软件来管。模型升级，工具 API 变化，产品需求变了，harness 也要跟着改。

难点在于，修改请求说的是行为，仓库摆放的是文件。开发者或负责改代码的智能体得先把「这个行为到底写在哪些代码里」找齐。论文把这件事叫行为定位。

Harness Handbook 的核心想法很朴素——别让智能体从文件树里硬猜行为。先整理出一张行为地图。再让它沿着地图找源码证据。

行为地图先于文件清单。Harness Handbook 关心的第一个问题是「这个系统运行时会做哪些事」。文件清单只是入口，行为链才是主线。

论文里的手册分三层。第一层是系统总览，回答架构、执行模型、主要阶段和全局数据流。读到这里，大概知道这个 Agent 是怎么跑起来的。

第二层是阶段和组件。初始化、规划、工具调用、观察回写、终止判断，各自承担什么责任，输入输出是什么，依赖哪些状态。

第三层才落到源码。它不只写「这里有个函数」。它还会说明这段单元逻辑负责什么行为，读写哪些状态，异常情况怎么走，并给出能回到当前仓库的源码定位器。

这三层真正有用的地方，在于把「我要改一个行为」翻译成「我该检查哪些代码和状态」。权限确认这类需求就是例子。错点往往不在某个函数本身。状态从规划阶段传到工具执行阶段，中途被谁覆盖了，才是问题。

开发者看到的是一条行为链，智能体拿到的是可验证的代码位点。状态索引也很重要。harness 里的很多 bug 不在单个函数里。它们出现在状态跨阶段传递时。

手册还有一条底线——源码仍然是权威。一个 L3 条目必须能在当前仓库里重新校验。校验失败，就冻结，不能继续拿来定位。这避免了最常见的文档病——代码早变了，文档还在装作自己正确。

手册怎么从代码里长出来？论文没有假设人手工写一本厚手册。它给的是自动构建流程。

这里的「叶」，指的是手册最终指向的最小单位。仓库结构清楚，它可以细到某个函数。仓库太大，或者阶段不清楚，就先粗到某个文件。这样能避免一开始就把上下文预算耗光。

第一步是静态分析。系统解析函数、方法、类、外部边界、调用关系和状态访问。结果是一个带源码位置的程序图。能解析就记录。不能解析的调用不会硬猜目标，只写进 unresolved log。

第二步才引入模型，目标是给代码贴行为标签。论文给了两种粒度。

执行阶段本来就清楚的仓库，比如已有可信的阶段骨架，用函数作叶。一个 L3 条目可以对应一个函数，也可以对应函数里的连续区域。实验里的 Terminus-2 走的是这条路。

仓库太大、阶段靠推断，或者函数级展开会超预算，就用文件作叶。系统先给文件做职责卡片。再推断阶段结构。实验里的 Codex 走的是这条路。

这里的关键，是把「不完整」显式留下来。没覆盖到的文件，无法稳定分类的逻辑，解析不了的调用，都进入记录。对代码修改任务来说，诚实暴露缺口，比伪装成完整地图更有用。

第三步是合成和打包。系统把阶段结构写成 L1、L2、L3 文档。每个 L3 重新锚回源码。系统还留下后续定位和同步需要的结构化数据。

改代码时，智能体怎么用它？有了手册，修改流程变成四步。

第一步，BGPD 先做定位。BGPD 的全称是 Behavior-Guided Progressive Disclosure——按行为逐层展开。它先从系统和阶段层确认相关行为。再钻到具体单元。最后把候选代码位点拿到当前仓库里校验。

第二步，规划器基于这些证据写编辑计划。计划不只是「改某文件」。它还要解释这些位点和请求为什么有关，哪些范围不该碰。

第四步，只要仓库产生非空 diff，手册就要同步更新。同步时先重校验源码定位器。再决定只刷新受影响条目，还是重新跑更大的组织流程。无法解析或无法分类的内容会被冻结，或者记入覆盖记录，避免混进正文制造假确定性。

这一步决定手册会不会变成又一本过期文档。很多团队的问题不是没写文档。代码改了三轮以后，文档还停在第一版架构图里。Harness Handbook 把重同步写进工作流，本质上是说——行为地图必须和仓库同版本。

实验真正想证明什么？论文评测聚焦在更靠前的一步。给定自然语言修改请求，规划器能不能找对实现位点，写出更好的编辑计划。自动合入补丁不在这次实验范围内。

这是一种主动缩小问题面的评测设计——先切到 Agent 改代码最容易出错的第一步。位置找错了，后面测试再多，也是在错误方向上补救。论文先证明「找位置」能改善，边界反而更清楚。

对照方式很干净。Baseline 直接探索仓库。Handbook-Assisted 用手册和 BGPD 导航。两组请求、仓库、模型、工具权限和解码设置一致。规划器使用 DeepSeek-V4-Pro。计划质量由三个评委独立判断——GPT-5.5、Opus 4.8、DeepSeek-V4-Pro。

评委看三件事——定位准不准，改动范围会不会过宽，推理证据是否充分。定位权重最高，占一半。

实验对象是两个开源 harness——Codex 和 Terminus-2。每个 harness 有 30 条行为驱动的修改请求。请求分三类。改已有行为但不给目标位置的 Query，请求跨文件能力的 Cross-file，还有关键词搜索很难命中的 Search-Hostile。

计划更好，token 还更少。Codex 上，手册辅助规划的胜率从 28.3% 到 38.3%。Terminus-2 上，从 26.7% 到 45.6%。三个评委的方向一致。结果不是某个评委模型偏好导致的。

同时，token 也降了。Codex 平均规划 token 从约 10.2 万降到 8.9 万。Terminus-2 从约 5.8 万降到 5.3 万。手册减少了无关探索。模型没有靠更长上下文硬撑结果。

这个提升也不能读成「有手册就稳了」。Codex 上 38.3% 的胜率仍然不高。它更像是省下了一部分乱搜仓库的时间，让规划器少走错路。距离确定性的代码修改流程还很远。

从分项看，收益最直接地体现在定位。手册先帮智能体少找错地方。范围控制和推理随之改善，幅度较小。这个结果符合直觉——找点错了，后面的计划写得再漂亮也没用。

弱规划器更接近强模型的位点判断。论文还做了一个更细的检查。把规划器预测的编辑位点，与 Opus 4.8、GPT-5.5 独立写出的参考计划对齐。看文件级和符号级的召回、精确率、F1，还有 Wrong。

Wrong 指的是预测与参考计划零重叠的比例。越低越好。

Table 1——相对 Opus 4.8 / GPT-5.5 参考计划的定位指标。文件级和符号级的召回、精确率、F1 共 24 组，Handbook 全部更高。Wrong 最大下降 25.9 个百分点。

这张表最重要的是一致性。两个 harness，两个参考模型，文件级和符号级，召回、精确率、F1 全部提升。F1 增益在 5.0 到 18.8 个百分点之间。

召回和精确率一起升。提升来自更准的位点集合。Wrong 也下降，完全找错方向的情况变少。Codex 对照 Opus 4.8 的符号级 Wrong 从 44.4% 降到 18.5%。这是很实在的差距。

但这里也要克制理解。参考计划仍然由模型写出，不能当成人工金标准。这个实验说明的是——在定位任务上，「弱规划器 + 好地图」更接近强模型的位点判断。它没有证明所有位点都绝对正确。

最适合关键字不友好的改动。按请求类型拆开看，六组 harness × 类型对比都偏向 Handbook。Codex 在 Query 请求上抬得最多。Terminus-2 在 Search-Hostile 请求上抬得最多。跨文件请求也有两位数百分点收益。

这部分给工程侧的启发更直接。改动集中在一个大家都知道的热文件里，手册价值有限。行为跨阶段、跨状态、跨模块，关键词又不稳定，行为地图就开始值钱。

它不适合拿来替代所有代码搜索。改按钮文案，改一个已知配置项，用 grep 可能更快。真正适合它的，是那种需求说的是「行为」，代码里却没有同名函数、还牵涉提示词、状态和工具边界的改动。

这也解释了为什么 harness 特别适合这类方法。普通业务函数常常靠调用链和测试覆盖定位。Agent harness 的行为更像运行时协议。很多关键逻辑藏在提示、状态、工具边界和异常分支里。

它离自动自我进化还有多远？论文附录里展示了手册如何以 SKILL.md 形态暴露给规划器。

这张图有点像给未来工作埋接口。真正难的是让手册持续可信——阶段标签准不准，源码锚点会不会漂，diff 后有没有及时重同步，覆盖缺口有没有暴露出来。

这篇论文的边界也很清楚。它解决的是改前定位和编辑计划，不保证改后行为正确。合入、测试、回归、旁路审查，仍然要靠现有工程流程。

我更愿意把 Harness Handbook 看成一种「行为索引层」。它介于仓库和负责改代码的智能体之间。它专门回答一个问题——这条行为是怎么在代码里长出来的。

如果未来的 Agent 真要长期维护自己的 harness，只会写补丁不够。它还得知道补丁该落在哪里，为什么这些位置算完整，改完后手册有没有跟着变。缺了这层行为地图，所谓自我进化很容易变成一次次带着高置信度的盲改。

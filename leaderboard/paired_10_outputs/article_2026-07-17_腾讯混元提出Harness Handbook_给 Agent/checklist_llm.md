腾讯混元 HY LLM Frontier 出了个新东西。叫 Harness Handbook。

说白了，它想把 Agent harness 的「行为」整理成一本手册。能导航。能校验。还能跟着代码一起更新。干嘛用的？让负责改代码的智能体先把该改的位置找齐，再写编辑计划。

论文全名挺长。Harness Handbook: Making Evolving Agent Harnesses Readable, Navigable, and Editable。

给编码 Agent 加一条规则。「删文件前必须问用户」。听着是个特别小的需求。是吧？

真上手你就知道了。问题散得一塌糊涂。

系统提示里可能写着安全规则。工具包装层可能决定这次删除放不放行。状态管理里没准存着用户授权。配置里可能还藏了个绕过确认的开关。遥测那边还会把这次危险操作记下来。

你去搜 delete、confirm、permission。搜出来全是碎片。

少看一块，场面就挺尴尬。提示词说要确认。某条执行路径照样绕过去。

论文想处理的，就是这事儿。

今天 Agent 外面裹着一层 harness。提示怎么拼。工具怎么调。状态怎么传。失败怎么办。权限怎么查。全归这层软件管。

模型升级了，harness 得改。工具 API 变了，harness 得改。产品需求变了，harness 还得改。

难就难在这儿。修改请求说的是「行为」。仓库里摆的是「文件」。开发者，或者说那个负责改代码的智能体，得先把「这行为到底写在哪几块代码里」找出来。

论文管这事儿叫行为定位。

Harness Handbook 的想法其实很朴素。别让智能体对着文件树硬猜行为。先把整个仓库理成一张行为地图。再让它顺着地图去找源码证据。

行为地图排在文件清单前面。它最先问的是「这系统跑起来到底会做哪些事」。文件清单只是个入口。行为链才是主线。

手册分三层。

第一层，系统总览。回答架构怎么搭、执行模型是什么、有哪几个主要阶段、全局数据怎么流。读到这儿，你大概知道这 Agent 是怎么跑起来的了。

第二层，阶段和组件。初始化。规划。工具调用。观察回写。终止判断。每块担什么责任。输入输出是什么。依赖哪些状态。

第三层才落到源码。它不光写「这里有个函数」。它还会说这段逻辑管什么行为，读写哪些状态，出异常往哪儿走，再给你一个能回到当前仓库的源码定位器。

这三层真正值钱的地方在哪？在于它把「我要改个行为」翻译成了「我该查哪些代码、哪些状态」。

拿权限确认来说。错的地方常常不在某个函数本身。而是状态从规划阶段传到工具执行阶段的时候，被谁给覆盖了。

开发者看到的是一条行为链。智能体拿到的是能验证的代码位点。

状态索引也很重要。harness 里的很多 bug 根本不在单个函数里。它们出在状态跨阶段传递的那一下。

手册还有条底线。源码才是权威。

一个 L3 条目，必须能在当前仓库里重新校验。校验不过，就冻结。不许再拿它去定位。

最常见的文档病是什么？代码早改了，文档还杵在那儿装自己是对的。这条底线就是来治这个的。

手册怎么从代码里长出来？论文可没假设有人手工写一本厚册子。它给的是一套自动构建流程。

先说「叶」。你可以把它理解成手册最终指向的最小单位。仓库结构清楚，它能细到某个函数。仓库太大、阶段又模糊，就先粗到某个文件。别一上来就把上下文预算烧光。

流程第一步，静态分析。

系统解析仓库里的函数、方法、类、外部边界、调用关系、状态访问。拼出一张带源码位置的程序图。能解析的就记下来。解析不了的调用不硬猜目标，只丢进 unresolved log。

第二步才把模型请进来。目的是给代码贴行为标签。论文给了两种粒度。

要是仓库的执行阶段本来就清楚，比如已经有一套可信的阶段骨架，那就用函数当叶。一个 L3 条目可以对应一个函数，也可以对应函数里头连续的一小段。实验里的 Terminus-2 走的是这条路。

要是仓库太大、阶段得靠猜，或者函数级展开会超预算，那就用文件当叶。系统先给每个文件做张职责卡片，再反推阶段结构。实验里的 Codex 走的是这条。

这里有个点我挺喜欢。「不完整」会被明明白白留着。没覆盖到的文件。没法稳定分类的逻辑。解析不了的调用。统统进记录。

对改代码来说，诚实暴露缺口，比装成一张完整地图有用多了。

第三步，合成加打包。系统把阶段结构写成 L1、L2、L3 文档。每个 L3 重新锚回源码。再留下一堆结构化数据，供后面定位和同步用。

改代码的时候，智能体到底怎么用？有了手册，流程大概是这样几步。

第一步，BGPD 先定位。BGPD 全称 Behavior-Guided Progressive Disclosure。说人话就是「按行为一层层展开」。它先在系统和阶段层确认相关行为，再钻到具体单元，最后把候选代码位点拿到当前仓库里校验一遍。

第二步，规划器拿着这些证据写编辑计划。这计划不只是「改某个文件」。它还得说清楚，为什么这些位点跟请求有关，哪些范围碰不得。

改完还有一步，也是最容易被忽略的一步。只要仓库产生非空 diff，手册就得同步更新。同步时先重校验源码定位器。再决定是只刷新受影响的条目，还是重跑一套更大的组织流程。解析不了、分类不了的内容，会被冻结或者记进覆盖记录。别让它混进正文制造假确定性。

这一步决定手册会不会变成又一本过期文档。很多团队不是没写文档。是代码改了三轮，文档还停在第一版架构图上。Harness Handbook 把重同步写进工作流。它其实在说一句话：行为地图必须跟仓库同版本。

实验真正想证明什么？论文评测卡在更靠前的一步。给它一句自然语言修改请求，规划器能不能找对实现位点，能不能写出更好的编辑计划。自动合入补丁？这次不做。

这是一种主动缩小问题面的评测设计。先把刀口对准 Agent 改代码最容易翻车的第一步。位置找错了，后面测再多，也是在错误方向上补救。先证明「找位置」能变好，边界反而更清楚。

对照方式很干净。Baseline 直接探索仓库。Handbook-Assisted 用手册加 BGPD 导航。两组用的请求、仓库、模型、工具权限、解码设置，全一样。

规划器用的是 DeepSeek-V4-Pro。计划质量交给三个评委独立判断：GPT-5.5、Opus 4.8、DeepSeek-V4-Pro。

评委看三件事。定位准不准。改动范围会不会铺太宽。推理证据够不够。定位权重最高，占一半。

实验对象是两个开源 harness：Codex 和 Terminus-2。每个 harness 各 30 条行为驱动的修改请求。请求分三类。改已有行为但不给目标位置的，叫 Query。要跨文件能力的，叫 Cross-file。关键词搜索很难命中的，叫 Search-Hostile。

计划更好，token 还更少。

Codex 上，手册辅助的胜率从 28.3% 涨到 38.3%。Terminus-2 上，从 26.7% 涨到 45.6%。三个评委方向一致。说明这结果不是某个评委的偏好带出来的。

token 也降了。Codex 平均规划 token 从大约 10.2 万降到 8.9 万。Terminus-2 从大约 5.8 万降到 5.3 万。手册把无关探索砍掉了。模型没靠堆长上下文硬撑。

不过别把这提升读成「有手册就稳了」。Codex 上 38.3% 的胜率真不算高。它更像省下了一部分乱搜仓库的时间，让规划器少走点弯路。离确定性的代码修改流程，还远着呢。

拆开看分项，收益最直接落在定位上。手册先帮智能体少找错地方。范围控制、推理质量跟着改善，但幅度小一些。这也符合直觉。找点找错了，后面计划写得再漂亮也白搭。

弱规划器更接近强模型的位点判断。

论文还做了个更细的检查。它把规划器预测的编辑位点，跟 Opus 4.8、GPT-5.5 独立写出的参考计划对齐。看文件级和符号级的召回、精确率、F1，还有 Wrong。

Wrong 是什么？预测和参考计划零重叠的比例。越低越好。

Table 1 讲的是相对 Opus 4.8 / GPT-5.5 参考计划的定位指标。文件级和符号级的召回、精确率、F1，一共 24 组。Handbook 全部更高。Wrong 最多降了 25.9 个百分点。

这张表最要紧的是一致性。两个 harness。两个参考模型。文件级加符号级。召回、精确率、F1，全涨。F1 增益落在 5.0 到 18.8 个百分点之间。

召回和精确率一起升，说明提升来自更准的位点集合。Wrong 也在降，完全找错方向的情况变少了。Codex 对照 Opus 4.8，符号级 Wrong 从 44.4% 掉到 18.5%。这是很实在的差距。

这里也得克制。参考计划毕竟还是模型写的，不能当人工金标准。这个实验说明的是，在定位任务上，「弱规划器 + 好地图」更接近强模型的位点判断。它没证明所有位点都绝对正确。

最适合关键词不友好的改动。

按请求类型拆开看，六组 harness × 类型的对比全偏向 Handbook。Codex 在 Query 请求上抬得最多。Terminus-2 在 Search-Hostile 请求上抬得最多。跨文件请求也有两位数的百分点收益。

这部分给工程侧的启发更直接。改动要是集中在一个大家都熟的热文件里，手册价值有限。可一旦行为跨阶段、跨状态、跨模块，关键词又不稳，行为地图就开始值钱了。

所以它不是来替代所有代码搜索的。改按钮文案，改一个已知配置项，grep 可能更快。真正适合它的，是那种需求嘴里说着「行为」，代码里压根没有同名函数，还牵着提示词、状态、工具边界的改动。

这也解释了为什么 harness 特别适合这套方法。普通业务函数，靠调用链和测试覆盖往往能定位。Agent harness 的行为更像一套运行时协议。关键逻辑藏在提示里、状态里、工具边界里、异常分支里。

它离自动自我进化还有多远？论文附录里展示了手册怎么以 SKILL.md 的形态暴露给规划器。

这张图有点像给未来埋了个接口。真正难的是让手册一直可信。阶段标签准不准。源码锚点会不会漂。diff 之后有没有及时重同步。覆盖缺口有没有露出来。

所以这篇论文的边界也很清楚。它管的是改前定位和编辑计划。改完以后行为对不对，它不保证。合入、测试、回归、旁路审查，还得靠现有工程流程。

我更愿意把 Harness Handbook 看成一层「行为索引」。它夹在仓库和负责改代码的智能体中间，专门回答一个问题：这条行为，是怎么在代码里长出来的？

将来 Agent 要是真要长期维护自己的 harness，光会写补丁可不够。它还得知道补丁该落在哪儿。为什么这些位置算完整。改完以后手册有没有跟着变。缺了这层行为地图，所谓自我进化，很容易变成一次次带着高置信度的盲改。
